 ClawdBot 情境智能 — 6-Tuple 物理状态模型分析文档

 版本: v1.0 | 日期: 2026-03-02 | 作者: AI Analysis

 ---
 Executive Summary

 本文档分析了以 6-tuple 物理状态 (time, location, motionState, phoneState, ambientLight, ambientSound) 作为情境智能核心状态表示的可行性。

 核心结论

 1. 7-tuple 可行性: 分析了 72 个日常场景，采用 7 维状态模型 (time, location, motion, phone, light, sound, dayType)。其中 55 个 (76%) 可完全由
 7-tuple 表示（isWeekend 从数字条件提升为状态维度后，S32 周末宅家等场景不再需要数字条件），12 个 (17%) 需要 7-tuple + 数字条件，5 个 (7%)
 是纯数字条件（设备告警）。7-tuple 作为物理世界状态表示是充分的。
 2. 状态空间: 7 维离散空间大小为 9×10×7×6×4×5×3 = 226,800 种理论组合。实际有效组合约 300-600 种（大量组合在物理上不可能，如 location=gym +
 motion=driving）。
 3. 场景覆盖: 72 个场景涵盖 12
 个生活类别（晨起、通勤、工作、居家、睡眠、运动、用餐、购物、旅行、社交、健康、设备），覆盖了一个普通人日常生活的主要情境。
 4. RL 模型推荐: 场景化推荐分为两个子问题——场景识别（确定性模式匹配，不需要 RL）和推荐选择（RL 学习用户偏好）。推荐分阶段策略：
   - Phase 1: 扩展现有 Stream MLP (25→34 dim) + LinUCB (8→14 dim)
   - Phase 2: 添加 Hierarchical Contextual Bandit（按场景类别）
   - Phase 3: 引入 GRU 序列模型（远期）
 5. 7-tuple 的局限: 无法区分时长（需要 activityDuration）；无法区分飞行阶段（需要 flightCountdownMin）。这些由设计中的 digitalConditions
 机制补充。相比原 6-tuple，新增 dayType 维度解决了周末/工作日/假日区分问题。

 Dim 7: DayType — 3 values (新增)

 ┌─────────┬────────────────────────────┬────────────────────────────────────────────┐
 │  Value  │         Detection          │                 Rationale                  │
 ├─────────┼────────────────────────────┼────────────────────────────────────────────┤
 │ workday │ dayOfWeek 1-5 且非法定假日 │ 工作日模式（通勤、会议、加班等）           │
 ├─────────┼────────────────────────────┼────────────────────────────────────────────┤
 │ weekend │ dayOfWeek 0 或 6           │ 周末模式（赖床、休闲、社交等）             │
 ├─────────┼────────────────────────────┼────────────────────────────────────────────┤
 │ holiday │ 法定假日或用户标记的休息日 │ 假日模式（类似周末但可能有旅行等特殊安排） │
 └─────────┴────────────────────────────┴────────────────────────────────────────────┘

 holiday 检测: 通过日历插件 (CalendarPlugin) 检测法定假日事件，或用户在设置中手动标记。初期可简化为 isWeekend 二值，后续扩展为三值含 holiday。

 加入 dayType 的影响:
 - 状态空间: 9×10×7×6×4×5×3 = 226,800 种理论组合（比 6-tuple 的 64,800 增加 3.5 倍）
 - 有效组合仍约 300-600 种（物理不可能的组合同样被排除）
 - 直接解决了 S32 周末宅家等场景的区分问题，不再需要 isWeekend 数字条件
 - 同一物理状态在工作日 vs 周末有完全不同的推荐（如 morning+home+stationary: 工作日=催促出门，周末=享受慢生活）

 Category 1: 早晨起床 (Morning Routine) — 6 scenarios

 S01 工作日早起 dayType=workday
 Step 0: (dawn, home, stationary, charging, dark, silent, workday)     — 闹钟响/自然醒
 Step 1: (dawn|morning, home, walking, in_use, dim, quiet, workday)    — 起床洗漱
 Step 2: (morning, home, stationary, in_use, normal, quiet, workday)   — 吃早餐/准备
 - 7-tuple覆盖: ✅ 完全覆盖。dark→dim→normal 的光线变化和 charging→in_use 的手机状态变化精确描述了起床过程。dayType=workday 区分于周末。

 S02 周末赖床 dayType=weekend|holiday
 Step 0: (morning, home, stationary, charging, dark, silent, weekend|holiday) — 还在睡

 - 7-tuple覆盖: ✅ dayType=weekend|holiday + time=morning + light=dark + phone=charging 精确识别赖床。无需额外数字条件。

 状态空间大小分析

 理论状态空间: 9 × 10 × 7 × 6 × 4 × 5 × 3 = 226,800 种组合

 物理不可能的组合 (排除后):
 - location=gym + motion=driving — 不可能
 - light=bright + time=sleeping — 极罕见
 - location=commute + motion=stationary + phone=charging — 矛盾
 - sound=noisy + time=sleeping + location=home — 极罕见
 - dayType=holiday + location=work — 少见（加班除外）

 估计有效组合: ~300-600 种 (约占理论空间的 0.1-0.3%)

 场景覆盖的组合数: 72 个场景 × 平均 1.4 步/链 ≈ 99 个状态点。每个状态点因通配符覆盖多个组合，估计覆盖约 400-500 种有效组合。

 结论: 72 个场景可以覆盖绝大多数有效物理状态组合。少量未覆盖的组合可以通过通配符场景或 fallback 规则处理。

 Part 4: RL Model Analysis & Recommendation

 当前 RL 架构

 ┌────────────┬────────────┬───────────────────────────┬─────────────────┐
 │   Model    │ Input Dims │       Architecture        │      Role       │
 ├────────────┼────────────┼───────────────────────────┼─────────────────┤
 │ MAB        │ 0          │ Epsilon-greedy (ε=0.1)    │ 冷启动 fallback │
 ├────────────┼────────────┼───────────────────────────┼─────────────────┤
 │ LinUCB     │ 8          │ Ridge regression per arm  │ 上下文感知探索  │
 ├────────────┼────────────┼───────────────────────────┼─────────────────┤
 │ Stream MLP │ 25         │ 25→128→64→1 per arm, ObGD │ 深度在线学习    │
 └────────────┴────────────┴───────────────────────────┴─────────────────┘

 混合评分: score = ruleConfidence × priority × (1 + 0.3 × tanh(MLP_output))
 - 0-5 samples: 纯规则
 - 5-20 samples: RL 逐渐介入 (0→30%)
 - 20+ samples: 满 RL (30%)

 场景化推荐的核心问题

 引入场景链后，推荐系统分为两个子问题:

 子问题 1: 场景识别 (State → Scenario)

 "用户当前在哪个场景的哪一步？"

 这不是 RL 问题。场景匹配是确定性模式匹配:
 - 输入: 当前 PhysicalState 6-tuple
 - 输出: 匹配的场景 + 当前步骤位置
 - 方法: ScenarioMatcher (规则引擎, 无需学习)

 子问题 2: 推荐选择 (Scenario + Context → Best Action)

 "在这个场景步骤，应该推荐什么？"

 这是 RL 问题。同一个场景步骤可能有多个候选推荐，需要学习用户偏好。

 RL 模型选型分析

 Option A: 扩展现有 Stream MLP (推荐 ✅)

 方案: 将 6-tuple 编码为特征，替换 Stream MLP 的部分输入维度，增加场景上下文特征。

 新特征向量 (34维, 替换原25维):
 7-Tuple Encoded (22 dims):
   [0-1]   hour sin/cos (2)           — 保留原有
   [2-3]   dayType one-hot (2)        — 新: weekend, holiday (workday=both 0)
   [4-12]  location one-hot (9)       — 新: home,work,commute,restaurant,gym,transit_hub,shopping,outdoor,cafe
   [13-18] motion one-hot (6)         — 新: stationary,walking,running,cycling,driving,transit
   [19-23] phone one-hot (5)          — 新: in_use,on_desk,in_pocket,charging,unknown
   [24-25] light ordinal (2)          — 新: dark=0,dim=0.33,normal=0.67,bright=1 (1 dim) + dark_flag
   [26-27] sound ordinal (2)          — 新: silent=0..noisy=1 + has_voice

 Scenario Context (6 dims):
   [28]    has_active_scenario (1)    — 是否有匹配的场景
   [29]    chain_position (1)        — 当前步骤/总步骤 (0~1)
   [30]    scenario_category_hash (1) — 场景类别编码 (commute=0.1, work=0.3, home=0.5, ...)
   [31]    is_routine (1)            — StateTransitionTracker 已有
   [32]    time_in_state_norm (1)    — 当前状态持续时间(归一化)
   [33]    battery_norm (1)          — batteryLevel/100 (保留原有)

 Total: 34 dims → 128 → 64 → 1

 优点:
 - 最小改动: 只改特征编码，网络架构不变 (34→128→64→1)
 - 利用现有 ObGD 在线训练: 无需重训
 - 冷启动策略不变 (MAB → LinUCB → MLP ramp)
 - 6-tuple编码比原始40+字段的子集更语义化、更紧凑

 缺点:
 - 无法建模序列依赖 (不知道"之前发生了什么")
 - 场景类别的 hash 编码不够精确

 适合: 当前阶段 (从28规则扩展到70场景的过渡期)

 Option B: 层级上下文 Bandit (Hierarchical Contextual Bandit)

 方案: 两层结构
 - Level 1: 场景选择 (确定性)
 - Level 2: 每个场景类别一个 LinUCB 实例

 ScenarioMatcher → scenarioCategory
                       ↓
             LinUCB_commute (d=12)
             LinUCB_work (d=12)
             LinUCB_home (d=12)
             LinUCB_travel (d=12)
             ...

 特征向量 (per-category, d=12):
 [0-1]   hour sin/cos
 [2]     chain_position
 [3]     is_routine
 [4]     time_in_state
 [5-8]   phone state one-hot
 [9-10]  light ordinal + sound ordinal
 [11]    isWeekend

 优点:
 - 每个类别的模型更小、学习更快
 - LinUCB 探索奖励量化不确定性
 - 同类别场景共享学习 (如"早通勤"和"晚通勤"共享 commute model)

 缺点:
 - 跨类别不共享学习
 - 需要管理多个模型实例
 - 冷启动问题在每个类别内独立

 适合: 中期 (当数据量足够每个类别独立学习时)

 Option C: Sequence-Aware RL (RNN/Attention)

 方案: 用 GRU/LSTM 编码状态链历史，输出推荐分数。

 state_t-3 → state_t-2 → state_t-1 → state_t
    ↓           ↓           ↓           ↓
  GRU_cell → GRU_cell → GRU_cell → GRU_cell → hidden
                                                  ↓
                                            Linear → score

 输入: 最近 N 个 PhysicalState (N=4~8), 每个编码为20维
 隐藏: GRU hidden 32维
 输出: 每个候选动作的分数

 优点:
 - 真正建模序列 ("早上从家出发开车" 后续应推荐导航)
 - 可以学习状态转移概率
 - 最强大的建模能力

 缺点:
 - 在线训练 GRU 很困难 (梯度爆炸/消失)
 - 需要大量数据
 - 计算开销高
 - 在手机端实现复杂

 适合: 远期 (当有足够数据和算力时)

 Option D: 6-Tuple State-Action Q-Table

 方案: 将6-tuple离散化为 state key, 建立 Q-table.

 state_key = "morning|home|stationary|charging|dim|quiet"
 Q[state_key][action_id] = running average of rewards

 优点:
 - 极其简单
 - O(1) 查找
 - 可解释

 缺点:
 - 状态空间太大 (9×10×6×6×4×5 = 64,800)
 - 大多数 state-action pair 永远不会被访问
 - 无法泛化 (相似状态不共享信息)

 不推荐: 状态空间爆炸问题严重。
