## 1. 概述

### 1.1 愿景

在手机里放一个 **AI 秘书**，它能够：
- **感知** — 收集物理世界和数字世界的数据
- **理解** — 知道用户的需求和意图
- **行动** — 在合适的时机提供帮助

### 1.2 核心原则

| 原则 | 说明 |
|------|------|
| **独立人格** | AI 是伙伴，不是附属品；有自己的观点和边界 |
| **隐私优先** | 用户控制 AI 能看到什么，默认最小权限 |
| **本地优先** | 个人数据不离开设备，学习在本地完成 |
| **渐进智能** | 从规则到模型到 LLM，按需升级复杂度 |

## 3. 感知插件系统

### 3.1 插件注册三要素

```
┌─────────────────────────────────────────┐
│              感知插件                    │
├─────────────────────────────────────────┤
│ 1️⃣ 类别注册 (Category)                  │
│    - 物理/数字世界                       │
│    - 域/子域                            │
│    - 默认隐私级别                        │
├─────────────────────────────────────────┤
│ 2️⃣ 分类器 (Classifier)                  │
│    - 小模型 or 规则函数                   │
│    - 输入：原始数据                       │
│    - 输出：分类标签 + 置信度              │
├─────────────────────────────────────────┤
│ 3️⃣ 编码器 (Encoder)                     │
│    - 输出特征向量（给RL用）               │
│    - 输出摘要（给LLM用）                  │
└─────────────────────────────────────────┘
```

### 3.2 物理世界 vs 数字世界

| 维度 | 物理世界 | 数字世界 |
|------|---------|---------| 
| **原始数据** | 数值流（连续） | 文本/结构化（离散） |
| **分类器** | 信号分类 | 内容分类 + NLP |
| **输出** | 特征向量为主 | 原始内容 + 特征 |
| **隐私处理** | 统一脱敏 | 分级过滤 |
| **LLM需求** | 摘要即可 | 可能需要原文 |

### 3.3 编码器输出规范（v2 更新：概率分布）

v1 的编码器输出单一标签（如 `label: "home"`），但现实中传感器数据是模糊的——GPS 精度65米时，"家"和"附近超市"都在误差范围内。

**v2 改进：编码器输出所有候选类别的置信度分布，而不是单一标签。**

```typescript
interface PluginEncoder {
  encode(rawData: SensorData): EncodedOutput;
}

interface EncodedOutput {
  // 概率分布：类别 → 置信度 (0~1)
  // 不要求归一化（multi-label，非互斥）
  // 例: { home: 0.80, market: 0.70 } 两个都有可能
  distribution: Map<string, number>;
  
  // 特征向量（给 RL 用）
  features: number[];
  
  // 文本摘要（给 LLM 用）
  summary?: string;
  
  // 数据质量 0~1（传感器精度、数据时效性）
  // GPS精度200米 → quality=0.3; 精度10米 → quality=0.95
  // 作为分布可信度的全局折扣
  quality: number;
}
```

#### 各插件分布输出示例

| 插件 | 分布输出示例 | 说明 |
|------|------------|------|
| **位置** | `{home: 0.8, market: 0.7, office: 0.02}` | GPS 精度差时多个地点都有概率 |
| **运动** | `{still: 0.6, walking: 0.3, driving: 0.1}` | 等红灯时静止和开车都可能 |
| **时间段** | `{morning: 0.9, commute: 0.7}` | 7:00 既是早上也是通勤时间 |
| **噪音** | `{quiet: 0.4, office: 0.5, cafe: 0.3}` | 环境音不确定 |
| **情绪** | `{neutral: 0.5, stressed: 0.3, relaxed: 0.2}` | 推断本身就不确定 |

> **注意：** 概率不要求加起来等于1。这是 multi-label 置信度，不是互斥的 softmax。
> 例：`home: 0.8` 和 `market: 0.7` 同时存在，因为 GPS 误差范围内两个地方都可能。

## 4. 意图识别

### 4.1 架构概述（v2 更新）

Layer 1 和 Layer 2 融合为**决策树 + RL 叶节点**架构：

```
        输入事件 + 上下文
              ↓
┌───────────────────────────────┐
│  决策树匹配（自动编译）         │  处理 95%
│  ├─ 树结构 = 规则（可解释）     │  延迟 < 1ms
│  └─ 叶节点 = RL 动作选择       │  延迟 < 5ms
└──────────────┬────────────────┘
               ↓ 未命中任何叶节点
┌───────────────────────────────┐
│  Layer 3: LLM 推理             │  处理 5%
│  延迟 100-500ms                │  复杂/模糊场景
└───────────────────────────────┘
```

### 4.2 用户规则配置

用户以平铺方式编写规则（直觉友好），每条规则由 key-value 条件对组成：

```typescript
interface SmartRule {
  id: string;
  name: string;                      // 用户可读名称，如"通勤提醒"
  enabled: boolean;
  
  // 触发条件（AND 关系，key-value 对）

  // 输出

interface RuleCondition {

  tolerance?: number;          // 容差，如时间 ±30min
}
```

### 4.3 自动编译决策树

规则由系统自动编译为决策树。**key 相同的条件自动合并**，不同的再分叉，避免重复判断。

#### 编译算法

```typescript
interface ExecNode {
  key: string;                                    // 判断哪个特征
  branches: Map<Object, ExecNode | LeafNode>;     // value → 下一步
  fallthrough?: ExecNode;                         // 没命中时继续（非停止）
}

interface LeafNode {
  rules: SmartRule[];      // 到达此叶子的候选规则
  rlPolicy?: RLPolicy;    // RL 学到的动作偏好
}

function compile(rules: SmartRule[]): ExecNode {
  if (rules.length === 0) return null;
  if (allConditionsMet(rules)) return makeLeaf(rules);
  
  // 1. 选择最优 key（成本感知 + 区分度）
  let bestKey = selectBestKey(rules);
  
  // 2. 按 value 分组
  let groups = groupByValue(rules, bestKey);
  
  // 3. 每组递归（去掉已判断的 key）
  let branches = new Map();
  for (let [value, subRules] of groups) {
    branches.set(value, compile(stripKey(subRules, bestKey)));
  }
  
  // 4. 没有这个 key 的规则走 fallthrough
  let noKey = rules.filter(r => !r.conditions.has(bestKey));
  let fallthrough = noKey.length > 0 ? compile(noKey) : null;
  
  return { key: bestKey, branches, fallthrough };
}
```

#### 成本感知的 Key 排序策略

编译时选 key 的优先级综合考虑**获取成本**和**区分度**：

```typescript
function selectBestKey(rules: SmartRule[]): string {
  let candidates = getAllKeys(rules);
  let best = '';
  let bestScore = -Infinity;
  
  for (let key of candidates) {
    let coverage = countRulesWithKey(rules, key) / rules.length;
    let distinctValues = countDistinctValues(rules, key);
    let cost = getFeatureCost(key);  // 获取成本
    
    // 区分度：不同 value 越多，一步分出的组越多
    let discrimination = distinctValues / rules.length;
    
    // 综合得分：覆盖率 × 区分度 / 成本
    let score = coverage * discrimination / cost;
    
    if (score > bestScore) {
      bestScore = score;
      best = key;
    }
  }
  return best;
}

// 特征获取成本（越小越便宜，应放在树的上层）
function getFeatureCost(key: string): number {
  const costs: Record<string, number> = {
    'weekday':   1,    // 内存直读，免费
    'hour':      1,    // 内存直读
    'charging':  1,    // 系统状态
    'battery':   1,    // 系统状态
    'keyword':   2,    // 字符串匹配
    'sender':    2,    // 查联系人
    'app':       2,    // 通知来源
    'location':  10,   // 可能需要 GPS 查询
    'activity':  10,   // 需要传感器推断
    'noise':     15,   // 需要麦克风采样
    'heartrate': 20,   // 需要蓝牙连手表
  };
  return costs[key] ?? 5;
}
```

**效果**：便宜的判断（时间、星期、电量）放在树的上层，昂贵的判断（GPS、传感器）放在下层。如果上层就排除了，就不需要查询 GPS，节省电量和延迟。

#### 编译示例

```
用户写了6条规则 → compile() 自动生成：

                    weekday? (cost=1)
                   /          \
                 true          false
                /                \
          hour? (cost=1)       hour?
```

#### 执行流程

```typescript
function evaluate(node: ExecNode, context: Record<string, Object>): LeafNode | null {
  // 1. 取当前 key 的实际值
  let actual = context[node.key];
  
  // 2. 在 branches 里找匹配（支持范围匹配）
  let next = matchBranch(node.branches, actual);
  
  // 3. 命中 → 继续深入
  if (next) {
    if (isLeaf(next)) return next;
    return evaluate(next, context);
  }
  
  // 4. 未命中 → 走 fallthrough（不是直接停止）
  if (node.fallthrough) {
    return evaluate(node.fallthrough, context);
  }
  
  // 5. 都没有 → 未匹配，交给 LLM
  return null;
}
```

规则变更时（增/删/改）→ 自动重新 `compile()` → 新树立即生效。

### 4.4 软匹配：从刚性到弹性（v2.0 新增）

传统决策树的每个判断是 true/false 二值的。现实中数据是模糊的（GPS 漂移、传感器缺失、边界时间），一个条件判断错了整条规则就失效。

**核心改进：每个条件返回 0~1 置信度，而不是 boolean。**

#### 问题场景

```
规则: weekday=true, hour=7:00~8:30, location=home → 通勤提醒

失败案例:
❌ GPS 漂移：在家，但定位到隔壁小区 → location≠home → 不触发
❌ 时间边界：6:55 起床，规则 7:00 才生效 → 不触发
❌ WiFi 断了：靠 SSID 判断"在家"，路由器重启 → 不触发
❌ 手表没连：靠心率判断"刚起床"，蓝牙断了 → 缺数据 → 不触发
```

#### 软匹配接口

```typescript
// 条件匹配返回置信度
interface MatchResult {
  confidence: number;    // 0.0 ~ 1.0
  source: string;        // 数据来源（调试用）
  stale: boolean;        // 数据是否过期
}
```

#### 各特征的软匹配策略

**时间：高斯衰减**
```typescript
function matchHour(actual: number, target: number, tolerance: number): number {
  let diff = Math.abs(actual - target);
  if (diff <= tolerance) return 1.0;
  return Math.exp(-0.5 * ((diff - tolerance) / (tolerance * 0.5)) ** 2);
}
// target=7:30, tolerance=30min:
// 7:30→1.0, 7:00→1.0, 6:50→0.85, 6:30→0.45, 6:00→0.05
```

**位置：多源融合**
```typescript
function matchLocation(target: string, sources: LocationSources): number {
  let scores: number[] = [];
  
  if (sources.gps) {  // GPS（如果有）
    let dist = distanceTo(sources.gps, getCoords(target));
    scores.push(dist < 50 ? 1.0 : Math.exp(-dist / 200));
  }
  if (sources.wifiSSID) {  // WiFi SSID（成本低）
    scores.push(sources.wifiSSID === getWifi(target) ? 0.95 : 0.1);
  }
  if (sources.btDevices.length > 0) {  // 蓝牙设备（家里的音箱等）
    let overlap = intersection(sources.btDevices, getKnownDevices(target));
    scores.push(overlap.length > 0 ? 0.8 : 0.2);
  }
  scores.push(getHistoricalLocationProb(target, now()));  // 历史推断
  
  return Math.max(...scores);  // 任一来源确认就行
}
```

**缺失数据：不知道 ≠ 不匹配**
```typescript
function matchFeature(key: string, context: Context): MatchResult {
  let value = context.get(key);
  if (value === undefined || value === null) {
    return { confidence: 0.5, source: 'missing', stale: true };
    // 0.5 = 中性，不确定，而不是0（否定）
  }
  // ... 正常软匹配
}
```

#### 决策树软执行

硬匹配的树只走一条路径；软匹配的树可以走多条路径，带权重。

感知插件的编码器已输出概率分布（见 3.3），决策树直接消费这些分布：

```typescript
function evaluateSoft(node: ExecNode, context: Context): RuleMatchResult[] {
  // 直接拿编码器输出的概率分布
  let dist = context.getDistribution(node.key);
  // 例: location → { home: 0.80, market: 0.70, office: 0.02 }
  
  let results: RuleMatchResult[] = [];
  
  for (let [value, child] of node.branches) {
    let conf = dist.get(value) ?? 0;
    
    // 乘以数据质量折扣
    conf *= context.getQuality(node.key);
    
    if (conf > 0.1) {  // 剪枝阈值
      if (isLeaf(child)) {
        results.push({ rule: child.rule, confidence: conf });
      } else {
        let subResults = evaluateSoft(child, context);
        for (let r of subResults) {
          r.confidence *= conf;  // 路径上的置信度相乘
          results.push(r);
        }
      }
    }
  }
  
  return results.sort((a, b) => b.confidence - a.confidence);
}

// 实际效果：
// location 分布 = { home: 0.80, market: 0.70 }, quality = 0.7
// 决策树 location 节点有两个分支：
//   home   → 通勤提醒 (上层conf × 0.80 × 0.7 = ×0.56)
//   market → 购物推荐 (上层conf × 0.70 × 0.7 = ×0.49)
// → 两条规则都被激活，按最终置信度排序
```

#### 置信度分级响应

```typescript
let best = results[0];

if (best.confidence > 0.8)       → 高置信度：直接执行
else if (best.confidence > 0.5)  → 中置信度：执行，但降低打扰（弹窗→静默通知）
else if (best.confidence > 0.3)  → 低置信度：交给 RL 决定要不要提醒
else                             → 太低：不触发
```

**关键设计原则：**
1. 每个条件返回置信度，不是 boolean
2. 缺失数据 = 0.5（不知道），不是 0（不匹配）
3. 位置等关键特征用多数据源融合（GPS + WiFi + 蓝牙 + 历史），取最高
4. 决策树可走多条路径，置信度沿路径相乘
5. 最终按置信度分级响应，低置信度交给 RL 兜底

#### 算法选择

|------|------|---------|-----------|---------|
| **Contextual Bandit** | 当前上下文 | 即时/批量 | ✅ 极轻 | 单次决策（通知/静默） |

**Contextual Bandit vs DQN 的核心区别：打扰预算**


```python
    elif user_response == 'click_slow':   base = +0.2   # 10分钟内点击

    recent_pushes = context['pushes_last_30min']
    disturbance_penalty = -0.1 * (recent_pushes ** 1.5)
    # 1次→-0.1, 2次→-0.28, 3次→-0.52, 5次→-1.12
    
    # 时段惩罚
    if context['sleeping']:
        disturbance_penalty *= 3        # 睡觉时打扰代价3倍
    elif context['meeting']:
        disturbance_penalty *= 2        # 开会时2倍
    
    # 正确性奖励
    if action == 'notify' and user_response in ['click_fast', 'thanks']:
        accuracy_bonus = +0.5           # 推对了
    elif action == 'silent' and was_actually_urgent(context):
        accuracy_bonus = -1.0           # 该通知没通知，严重惩罚
    else:
        accuracy_bonus = 0
    
    return base + disturbance_penalty + accuracy_bonus
```

#### 探索策略

RL 需要偶尔尝试新动作来发现更好的策略，但用户不喜欢被当实验品。

```python
def smart_explore(state, context):
    # 紧急事件不探索
    if context['priority'] == '🔴':
        return policy.best_action(state)
    
    # 根据风险动态调整探索率
    if context['user_idle'] and context['low_importance']:
        epsilon = 0.2       # 用户闲着 + 不重要 → 多探索
    else:
        epsilon = 0.05      # 其他时候少探索
    
    # Thompson Sampling（比 ε-greedy 更优雅）
    # 从后验分布采样，自然平衡探索和利用
    return thompson_sample(state, epsilon)
```

**探索原则：**
1. 🔴 紧急事件永远不探索，用最优策略
2. 低风险 + 用户闲着 → 多探索（ε=0.2）
3. 其他情况 → 少探索（ε=0.05）
4. 探索率随时间衰减（用户习惯稳定后减少）

### 4.6 RL 算法选择：LinUCB（v2 更新）

#### 为什么选 LinUCB

端侧在线学习的约束：每次反馈都能学、计算量极小（<0.1ms）、内存固定（~100KB）、数值稳定。

| 模型 | 单次更新计算量 | 内存 | 稳定性 | 在线学习友好度 |
|------|--------------|------|--------|--------------|
| 查表法 | O(1) | ~1KB | ✅ 完美 | ⭐⭐⭐⭐⭐ |
| **LinUCB** | **O(d²)** | **~100KB** | **✅ 好** | **⭐⭐⭐⭐⭐** |
| MLP (SGD) | O(d×h) | ~20KB | ⚠️ 需调参 | ⭐⭐⭐ |
| DQN | O(batch×d×h) | ~100KB+ | ❌ 不稳定 | ⭐⭐ |

**LinUCB 核心优势：**
1. **自带探索**（UCB 公式自动平衡探索/利用，无需设 ε）
2. **零超参数风险**（没有学习率、batch size、目标网络）
3. **增量学习天然支持**（A += xxᵀ 就是全部历史的编码）
4. **工业验证**（微软 Bing 个性化推荐，Li et al. 2010）

#### LinUCB 原理

```
每个动作维护一个线性模型：reward ≈ θᵀx

选动作：score = θᵀx + α√(xᵀA⁻¹x)
                ~~~~    ~~~~~~~~~~~~
                利用      探索（不确定性越大，探索越多）

更新：
  A ← γA + xxᵀ          // d×d 矩阵（γ=衰减系数）
  b ← γb + x × reward   // d维向量
  θ = A⁻¹b              // 解线性方程

d=40 时：单次更新 40²=1600 次乘法 → <0.01ms
内存：A(40×40) + b(40) × 10个动作 × 4字节 ≈ 70KB
```

#### 软匹配决策树 + LinUCB 融合（方案C：语义融合）

**问题：** 软匹配决策树输出多个叶节点的概率分布，不是确定的一个。标准 LinUCB 假设上下文确定。

```
软匹配结果：
  叶节点 #7 (工作日+早上+在家)    conf=0.80
  叶节点 #3 (工作日+早上+超市)    conf=0.70
  叶节点 #12 (周末+下午+在家)     conf=0.40

```

**方案对比：**

| 方案 | 做法 | 优劣 |
|------|------|------|
| A: 多实例加权 | 每个叶节点一个LinUCB，按置信度加权融合 | 反馈归因困难，奖励被稀释 |
| B: 叶节点ID作特征 | 一个全局LinUCB，叶节点ID展开为特征 | 维度随叶节点数增长，ID无语义 |
| **C: 语义融合** | **叶节点→语义向量→加权融合→一个全局LinUCB** | **维度固定，语义连续，反馈自然** |

#### 时间衰减（Discounted LinUCB）

标准 LinUCB 的 `A += xxᵀ` 只加不减，坏数据永远影响模型。加入衰减系数：

```cpp
// 标准（无遗忘）
A += x * xᵀ;      b += reward * x;

// 衰减（自动遗忘旧数据）
A = γ * A + x * xᵀ;    b = γ * b + reward * x;
// γ=0.999 → 半衰期 ≈ 693次（约1个月）
// γ=0.998 → 半衰期 ≈ 346次（约2周）
// γ=0.995 → 半衰期 ≈ 138次（约1周）
```

效果：用户换工作/搬家后，旧习惯在2-4周内自动淡出。

#### 异常检测

```cpp
struct FeedbackValidator {
    RingBuffer<float> recentRewards;  // 最近100条
    float runningMean, runningStd;
    
    bool isAnomaly(float reward, const VectorXf& x) {
        // 奖励偏离均值 3σ
        if (abs(reward - runningMean) > 3 * runningStd) return true;
        // 特征值超出合理范围
        for (int i = 0; i < x.size(); i++)
            if (abs(x[i]) > featureBounds_[i]) return true;
        // 短时间大量反馈（乱点）
        if (recentFeedbackRate() > 10_per_minute) return true;
        return false;
    }
};
```

#### C++ 实现

```cpp
class RobustLinUCB {
    int d_;
    float alpha_ = 1.0;
    float gamma_ = 0.998;
    
    struct ArmParams {
        MatrixXf A;   // d×d
        VectorXf b;   // d
        VectorXf theta;
        bool dirty = true;
    };
    vector<ArmParams> arms_;
    FeedbackValidator validator_;
    ModelCheckpoint checkpoint_;

    int selectAction(const VectorXf& x) {
        float bestScore = -INFINITY;
        int bestArm = 0;
        for (int i = 0; i < arms_.size(); i++) {
            if (arms_[i].dirty) {
                arms_[i].theta = arms_[i].A.ldlt().solve(arms_[i].b);
                arms_[i].dirty = false;
            }
            float exploit = arms_[i].theta.dot(x);
            float explore = alpha_ * sqrt(x.dot(arms_[i].A.ldlt().solve(x)));
            float score = exploit + explore;
            if (score > bestScore) { bestScore = score; bestArm = i; }
        }
        return bestArm;
    }
    
    void update(int arm, const VectorXf& x, float reward) {
        if (validator_.isAnomaly(reward, x)) return;  // 异常过滤
        reward = clamp(reward, -3.0f, 3.0f);          // 奖励裁剪
        arms_[arm].A = gamma_ * arms_[arm].A + x * x.transpose();
        arms_[arm].b = gamma_ * arms_[arm].b + reward * x;
        arms_[arm].dirty = true;
    }
};
```

### 4.14 动态阈值

触发阈值根据用户状态自动调整，减少不必要打扰：

```typescript
function getDynamicThreshold(context: Context): ThresholdConfig {
  let activity = context.get('activity');
  let hour = context.get('hour');
  
  // 基础阈值表
  const thresholds: Record<string, number> = {
    'driving':  0.95,   // 开车：只有非常确定才打扰
    'sleeping': 0.98,   // 睡觉：几乎不打扰
    'meeting':  0.90,   // 开会：高阈值
    'idle':     0.50,   // 闲着：低门槛
    'default':  0.70,
  };
  
  let base = thresholds[activity] ?? thresholds['default'];
  
  // 深夜加成
  if (hour >= 23 || hour < 7) base = Math.max(base, 0.90);
  
  return base;
}
```

**与 RL 结合：** 阈值可以作为 RL 的可学习参数——不同状态下的最优打扰阈值从用户反馈中学出来，替代手工设定。

```typescript
function privacyFilter(action: Action, context: Context): Action | null {
  let privacyLevel = getPrivacyLevel(action.requiredDataSource);
  
  switch (privacyLevel) {
    case '🔴':  // 禁止：直接阻断
      return null;
    case '🟡':  // 摘要：去除原文，只保留元信息

      return action;
    case '🔵':  // 临时授权：弹窗请求
```

```typescript
}

function selectTiming(priority: string, userState: string): DeliveryTiming {
  if (priority == '🔴') return { mode: 'immediate' };
  if (userState == 'active_using') return { mode: 'on_idle' };
  if (userState == 'screen_off') return { mode: 'on_unlock' };
  if (priority == '🟢' || priority == '⚪')
    return { mode: 'batched', batchWindow: 300_000 };  // 5分钟内合并
  return { mode: 'immediate' };
}
```

### 6.2 复合奖励函数（v2 更新）

基础反馈之外，叠加打扰惩罚和正确性奖励：

```python
def compute_reward(action, user_response, context):
    # 1. 基础反馈分（见6.1表）
    base = get_base_reward(user_response)
    
    # 2. 打扰惩罚（连续推送递增）
    recent = context['pushes_last_30min']
    disturbance = -0.1 * (recent ** 1.5)
    # 1次→-0.1, 2次→-0.28, 3次→-0.52, 5次→-1.12
    
    # 3. 时段加权
    if context['sleeping']:   disturbance *= 3   # 睡觉时打扰代价3倍
    elif context['meeting']:  disturbance *= 2   # 开会时2倍
    elif context['driving']:  disturbance *= 2.5 # 开车时2.5倍
    
    # 4. 正确性奖励
    accuracy = 0
    if action == 'notify' and user_response in ['click_fast', 'thanks']:
        accuracy = +0.5           # 推对了，用户确实需要
    elif action == 'silent' and was_actually_urgent(context):
        accuracy = -1.0           # 该通知没通知，严重失误
    elif action == 'silent' and not was_important(context):
        accuracy = +0.3           # 正确地没打扰
    
    return base + disturbance + accuracy
```

### 6.3 主动询问策略

```
频率: min(每天1次, 每10次重要决策后1次)

触发条件：
- AI 做了重要推荐
- 用户采纳或忽略后
- 不在用户忙碌时段

询问方式（低侵入）：
- "刚才的午餐推荐有帮助吗？👍/👎"
- 不要弹窗，用卡片/内联按钮
- 用户不回答 = 默认 +0.05（不惩罚）
```

### 6.4 防过拟合

```python
# 连续负反馈 → 暂停 + 道歉
if consecutive_negative >= 5:
    pause_category(intent, duration=24h)
    notify("看起来这类提醒打扰到你了，我先暂停一天")

# 低点击率 → 自动降级
if category_click_rate < 0.10:     # 10%以下
    downgrade_to_summary(intent)    # 从推送降级为摘要

# 长期无正反馈 → 衰减权重
if days_without_positive > 14:
    reduce_trigger_weight(intent, factor=0.5)
```
